# NanoAI v1.1 — Production Hardening

Transición de R&D a Release Candidate. Objetivo: el camino medido y estable
(**llama.cpp CPU + 1.5B ≈ 4.17 tok/s**) funcione **siempre**, no ganar más tok/s.

## Scope congelado

```text
BACKEND DE PRODUCCIÓN   llama.cpp CPU
MODELO DEFAULT          1.5B (Qwen2.5, Q4_K_M)
VULKAN                  experimental / disabled by default (NO-GO en CPH2557)
MNN                     experimental / unavailable (BLOCKED, ver abajo)
9B+                     advanced / non-interactive en este device
NPU/QNN                 future
```

## Estado de backends (medido, no asumido)

| Backend | Estado | Evidencia |
|---------|--------|-----------|
| llama.cpp CPU | ✅ PRODUCTION | 1.5B = 4.17 tok/s interactivo; 9B = 0.31 tok/s no-interactivo |
| Vulkan | ⚠️ SUPPORTED BUILD + NO-GO device | 1.5B = 0.73–2.52 tok/s, prefill 12s vs 1s (Mali-G57 MC2 sin matrix cores). Ver `docs/benchmarks/oppo-cph2557-vulkan.md` |
| MNN | ⛔ BLOCKED | tokenizer del artefacto preconvertido (formato GGUF) incompatible con runtime MNN (SentencePiece/Tiktoken). Ver `docs/benchmarks/oppo-cph2557-mnn.md` |
| OpenCL | ❌ no evaluado | GPU Mali/MediaTek; mismo riesgo que Vulkan |
| NPU/QNN | 🔜 future | no detectado |

## Perfil de producción del OPPO CPH2557

```text
SoC: MediaTek MT6833 (Dimensity 6100+)
GPU: Mali-G57 MC2 (matrix cores: none, 32KB shared)
RAM: 7.8 GB total

1.5B CPU → ~4.17 tok/s, INTERACTIVE ✅
9B  CPU → ~0.31 tok/s sustained, INTERACTIVE ❌
```

El planner lo decide vía `BackendProfile` (available ≠ recommended) + umbral
de decode (<1 tok/s = no interactivo). No se hardcodea `if device == CPH2557`;
se persiste `DeviceFingerprint` + `BackendBenchmark` medido.

## 7 gates de producción

| Gate | Criterio |
|------|----------|
| P1 Install | APK release instala/abre limpio |
| P2 Lifecycle | start/load/generate/unload/restart estable |
| P3 Memory | sin OOM ni crecimiento monotónico |
| P4 Recovery | kill/error/cancel no dejan runtime roto |
| P5 Sessions | KV + prefix cache coherentes |
| P6 Android | foreground/background/screen-off correctos |
| P7 Model safety | modelo inválido/lento/grande produce fallback/aviso |

## Prueba final (Release Candidate)

20 pasos manuales: install clean → chat → KV → prefix HIT → cancel → re-generar
→ background/foreground → cambiar modelo → volver 1.5B → screen-off → recovery
→ kill -9 server → auto-recovery → 30 turnos → unload/load → cerrar/reabrir.

Criterio: 0 crashes, 0 ANR, 0 OOM, 0 corrupción KV, 0 falsa desconexión,
0 respuesta tras cancel.
